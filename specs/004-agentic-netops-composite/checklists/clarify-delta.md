# Post-Clarification Delta Checklist: Agentic NetOps on Nokia SR Linux — Composite Platform

**Purpose**: Formal pre-implement gate testing the *quality of the requirements added after
`requirements.md` was written* — FR-102…FR-109, NFR-014, SC-042…SC-046, CR-008 and the rewordings
the three analysis passes made around them (FR-007, FR-015, FR-034, FR-062, FR-075, FR-078, NFR-003,
SC-028, SC-030). `requirements.md` carries no item for any of these ids.
**Created**: 2026-09-20
**Feature**: [spec.md](../spec.md) · cross-checked against [data-model.md](../data-model.md) and
[contracts/](../contracts/)

**Note**: This custom checklist is generated by the `$speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

**Scope boundary**: items test what is *written* in spec.md and whether data-model.md and the
contracts say the same thing. tasks.md is out of scope (three `/speckit-analyze` passes covered task
coverage). No item asks whether an implementation works.

## Requirement Completeness

- [ ] CHK001 Are the rules that bound the force-release — a non-empty reason is required, it is
      honoured only on an object that is deleting *and* blocked on an unreachable target, and neither
      tier identity may set it although FR-075 grants the deployer *update* on service intent
      objects — stated as requirements in the spec, or only as contract rows? [Gap, Spec §FR-103,
      §FR-075, contracts/reconciliation.md Rule 8, contracts/kubernetes-objects.md]
- [ ] CHK002 Is the consequence of an *open* force-release finding for later services (a render that
      would reproduce a named stale object is refused; the fabric reports degraded, not not-Ready)
      a requirement in the spec, given that it changes operator-visible acceptance behaviour?
      [Gap, Spec §FR-103, data-model §3 `status.findings[]`]
- [ ] CHK003 Does FR-103 define the outcome when the unreachable device never returns because it was
      removed from the fabric design, when more than one target is unreachable, and whether a
      force-release acts per service or per device? [Gap, Coverage, Spec §FR-103, Spec §Edge Cases]
- [ ] CHK004 Are the authentication behaviours the contracts add — unauthenticated probe routes
      (against "both surfaces MUST require an authenticated operator"), rotation without restart, a
      thread continued under a different credential, the fixed failed-attempt delay, refusal of a
      caller-supplied `principal`, loopback HTTP Basic with one operator as the reference scale —
      each traceable to a sentence of FR-102 or FR-019, or are they unanchored design?
      [Gap, Consistency, Security, Spec §FR-102, §FR-019, contracts/supervisor-http.md, data-model §22]
- [ ] CHK005 Does FR-106 state *how* an operator "explicitly clears" a stored base URL, whether the
      model name and API key of an existing Secret are preserved, replaced or merged on
      re-provisioning, and whether the no-base-URL refusal applies only at start-up or also when the
      Secret changes under a running agent? [Completeness, Edge Case, Spec §FR-106, quickstart §LLM]
- [ ] CHK006 Does FR-107 define what a scheduled re-verification reports when it *cannot run* — the
      target is unreachable or the read times out — as distinct from one that ran and found an
      invariant missing? [Gap, Spec §FR-107]
- [ ] CHK007 Does FR-107 state whether services that have never reported Ready, and services held in
      deletion, are inside the schedule (Rule 8 "requeues at the re-verification interval"), and
      does it bound the configurable interval — minimum, maximum, behaviour at zero or unset — as
      data-model §25 does for the other defaults? [Completeness, Spec §FR-107, data-model §25,
      contracts/reconciliation.md Rule 8]
- [ ] CHK008 Does FR-108 define recovery when verification tooling dies after writing scratch
      configuration or an injected fault and before removing it, given that "removed by the tool that
      wrote it" presumes the tool survives? [Gap, Exception Flow, Spec §FR-108]
- [ ] CHK009 Does FR-109 define what happens to a claim when the VNI of an *existing* service intent
      object is edited, given that claims are "released only by finalization"? [Gap, Spec §FR-109]
- [ ] CHK010 Does FR-109 define the outcome when a claim carries the object's correlation label but
      reports a *different* value than the object now carries — the state an out-of-band edit
      (FR-105) produces on a tier-created service? [Gap, Spec §FR-109, Spec §FR-105]
- [ ] CHK011 Does FR-109 define the provider's behaviour when the allocation authority is unreachable
      on the tier-less path, as the claim contract does for the tier path? [Gap, Spec §FR-109,
      contracts/kuid-claim-profiles.md §failure table]
- [ ] CHK012 Does FR-104 state the preconditions for a substitution — clean lab only, or may a lab
      holding upstream claims be switched — and whether a return to the upstream authority is
      permitted and how it is recorded? [Gap, Spec §FR-104]
- [ ] CHK013 Is the consequence specified if the capability gate shows the upstream authority binds
      ordinary claims but *not* a claim for a stated value — is that an FR-104 stop, or a narrower
      refusal of the tier-less path only? [Gap, Spec §FR-109, Spec §FR-104, research R-44]

## Requirement Clarity

- [ ] CHK014 Is "never defaulted" in FR-102 unambiguous about what it covers, given that the data
      model gives the username a default of `operator` and only the password is always generated?
      [Conflict, Spec §FR-102, data-model §22]
- [ ] CHK015 Is the representation FR-105 hashes specified in the requirement — the submitted bytes,
      or the server-side dry-run result with API defaults applied — and does it match the contract's
      "computed from the server-side dry-run result"? [Clarity, Spec §FR-105, contracts/network-spec.md]
- [ ] CHK016 Is FR-105's scope explicit on three points: whether a *removal* request for a service
      found modified outside the tier proceeds or is refused ("any further change is a new request");
      whether edits that do not touch `spec` — tier-owned labels and annotations, the hash annotation
      itself — count; and is SC-030's "100% of those injected" defined over the same set?
      [Ambiguity, Spec §FR-105, §FR-069, §FR-101, §SC-030]
- [ ] CHK017 Are the two distinct notions of out-of-band change — an edited *service intent object*
      (detect, never revert: FR-105) and an edited *device path* (repair: FR-015, FR-107) — named
      differently enough that "drift" cannot be read as either? [Clarity, Spec §FR-105, Spec §FR-015]
- [ ] CHK018 Are "scratch configuration", "a declared injected fault" and "a device client" in
      FR-108 defined precisely enough — where a fault is declared, what makes configuration scratch,
      what the CI boundary check matches — that two implementers would flag the same invocations?
      [Clarity, Measurability, Spec §FR-108]
- [ ] CHK019 Is the "name derived deterministically from the object" in FR-109 specified, or
      referenced, together with its behaviour at the object-name length limit and for two objects
      whose derived names would collide? [Clarity, Spec §FR-109, contracts/kuid-claim-profiles.md §8]
- [ ] CHK020 Does NFR-014 fix what a log consumer depends on — field names, the level set, the
      timestamp format, the output stream — or defer them explicitly to data-model §27, and is its
      restriction to *first-party* workloads a reasoned exclusion consistent with Principle IV's
      unqualified "logs MUST be structured"? [Clarity, Assumption, Spec §NFR-014, data-model §27,
      Constitution §IV]

## Requirement Consistency

- [ ] CHK021 Do FR-107 ("MUST set `Ready=False` … within that interval") and SC-044 ("within one
      re-verification interval plus one reconciliation interval") state the same bound?
      [Conflict, Spec §FR-107, Spec §SC-044, contracts/crd-api.md §conditions]
- [ ] CHK022 Is FR-015 internally coherent in saying production drift policy "MUST be selected
      explicitly and MUST NOT be inherited from the lab" while closing the set of policies at one
      member? [Consistency, Spec §FR-015]
- [ ] CHK023 Do FR-062, FR-109, the *Claim reference* entity, data-model §11 and the claim contract
      agree on who releases which claim in every removal path — decline, rollback, never-submitted,
      tier removal, cluster-tooling deletion, force-release? [Consistency, Spec §FR-062, §FR-109,
      contracts/kuid-claim-profiles.md §5]
- [ ] CHK024 Is the rule that an operator-named VLAN "is claimed on neither path" reconciled with
      allocated VLAN claims drawn from the same 100–4000 range — do the requirements say what stops
      the allocator from handing out a VLAN an operator has already named? [Gap, Conflict,
      Spec §FR-109, Spec §FR-034]
- [ ] CHK025 Does FR-078's "retained for the life of the lab and exported before teardown" agree
      with FR-102's "removed by the shutdown script" on ordering — is it a requirement that export
      and the SC-042 reconciliation precede credential removal? [Consistency, Spec §FR-078, §FR-102]
- [ ] CHK026 Does FR-107's added read load appear in the explicit sizing of the device management
      session limit that FR-086 requires "for the two together"? [Consistency, Spec §FR-107, §FR-086]
