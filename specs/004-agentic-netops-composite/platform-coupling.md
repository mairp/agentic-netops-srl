# Platform coupling: how each SONiC binding was resolved on SR Linux

**Feature**: `004-agentic-netops-composite` | **Date**: 2026-09-20

This file was the seam. It inventoried every place the merged composite was bound to **SONiC
specifically**, as opposed to bound to **a datacenter EVPN/VXLAN fabric generally**, so that a later
retargeting pass could see its whole surface at once instead of discovering it one compile error at
a time.

**The pass has happened.** This file is now the **resolution record**: every row keeps its number and
its original statement of the coupling, and gains a **disposition** and a **resolution on SR Linux**
with the retarget decision, the requirements that carry it, and the evidence section that proves it.
Nothing was resolved by assertion; every resolution cites a report under [evidence/](./evidence/).

SONiC-era terms appear in this file deliberately. It is a provenance document: the left-hand column
has to name what was there in order for the right-hand column to mean anything. They appear nowhere
in live requirement text — [spec.md](./spec.md) describes an SR Linux system and nothing else.

Rows are classified as they always were:

| Class | Meaning |
|---|---|
| **`platform-specific`** | Changes when the network operating system changes. The retarget rewrote or deleted it |
| **`platform-neutral`** | Survives any NOS unchanged. The retarget was not allowed to touch it |
| **`platform-adjacent`** | Survives, but its *content* moves. The requirement stands; the values, names or list inside it are replaced |

And each row now carries one disposition:

| Disposition | Meaning |
|---|---|
| `deleted` | The coupling has no successor. The concept does not exist on SR Linux, or the scope that needed it was deferred |
| `rewritten` | The obligation survives; its content is entirely new |
| `replaced` | A specific value, range or rule is swapped for the SR Linux one, one-for-one |
| `unchanged` | Confirmed untouched by the retarget |
| `resolved` | An open question the row was holding open is now answered |

**Read §History and §New couplings first if you are auditing this retarget**: the first records what
the old divergence was and why it stopped existing; the second records the couplings SR Linux
introduces that SONiC never had, so the next platform move starts from a complete seam rather than
from this one.

## History: the divergence this file used to carry, and what happened to it

The merged composite's most important section recorded a **disagreement between the specification
and the deployment**. It is not a coupling, it has no successor row, and it is kept here in short
form because deleting it would erase the reason three requirements are worded the way they are.

**What the divergence was.** The specification said the only southbound was
`provider → device-configuration Config → gNMI (JSON_IETF, TLS) → device`. The recorded deployment
was `pkg/fabricplan → cmd/fabric-executor → docker exec → redis-cli -n 4 hset` — a **host-side**
executor outside the cluster, contradicting FR-007, with access lists forced onto the raw store
because a YANG-invalid whole-config write was said to poison every subsequent whole-config write
image-wide. The 001 reconciliation sheet marked the specified direct path *never held*. Neither form
was canonicalised by the merge: the contract was carried because the specification said it, the
divergence because the evidence said it, and resolving them was left as an open decision.

**The new finding that changes the shape of the question.** The retarget research found that the
disagreement was larger than recorded, and in the other direction: the upstream control plane
**never ran either**. The predecessor's install scripts fetched CRD paths that do not exist
upstream — one pinned repository returns 404 — and **silently fell back to hand-written look-alike
CRDs in look-alike API groups** (`network.kubenet.dev`, `id.kuid.dev`, `sdc.sdcio.dev`), none of
which is an upstream group. The `Network` shape the entire data model rested on was a first-party
invention presented as an upstream API, carried in a CRD whose `spec` was
`x-kubernetes-preserve-unknown-fields: true` — that is, no schema at all
([evidence/05-kubenet-sdc-kuid.md](./evidence/05-kubenet-sdc-kuid.md) §0). So the choice was never
"restore or retain". Nothing was there to restore.

**How it is resolved.**

- **RD-02** makes `provider → device-configuration resource → gNMI (JSON_IETF, TLS) → SR Linux` the
  only southbound, with **no executor, no host-side component and no escape hatch**. FR-007 has no
  exception. Everything that existed for the other path is deleted, not deprecated: PC-11, PC-12,
  PC-13, the second half of PC-16, D-12, R-25, the raw-store client and the whole-config-versus-raw-store
  split. The hazard that justified the hatch was a property of the previous platform's configuration
  generator and has no analogue here (PC-12).
- **RD-03** answers ownership: a **first-party fabric API** (`fabric.agentic-netops.io/v1alpha1`,
  Kinds `Fabric` and `Network`, structural schemas, no preserve-unknown-fields on `spec`) and a
  single first-party provider that is the only renderer of any device path. The
  device-configuration layer and the allocation authority are reused unchanged, from their own
  pinned artefacts. The dormant upstream fabric control plane is a **reference design only**.
- **FR-098** makes the look-alike failure impossible to repeat by rule rather than by care: no CRD
  or API service may be installed into an upstream project's API group unless it is that project's
  own pinned, unmodified artefact, and provisioning must **fail** rather than fall back when an
  upstream artefact cannot be fetched.

The row is therefore closed. It is recorded, not carried.

## Predecessor defects and the requirement that now prevents each

Two further disagreements between the specification and the deployment travelled with the merge.
Neither was a property of SONiC — the first is a supply-chain defect and the second a check-scoping
defect — so neither is a coupling, and neither could be left to be inherited silently. Each is now
prevented by a requirement rather than described by a paragraph.

| Predecessor defect | What was specified | What was recorded | Prevented now by |
|---|---|---|---|
| **Image pinning** | Every image pinned by immutable digest; intent-tier images pinned with a local build step; any exception warned at provisioning time | Six intent-tier images ran as mutable `:latest` with no lock-file entry and **no warning**; placeholder digests persisted in four deployment manifests and two lock-file entries; one gate proof listed digests (`sha256:1111…`–`6666…`) that appear in no commit | **NFR-003, strengthened.** A placeholder or synthetic digest is forbidden outright, and the pin check MUST **resolve every digest against its registry**, so an unpullable or invented pin fails before provisioning rather than during it. Mutable references — `latest`, a floating minor tag, a branch — are forbidden wherever a reference can appear, explicitly including inside the device-configuration layer's schema definition, Grafana plugin installs and generator images. CR-006 carries the gate. **RD-15** |
| **Applied-side verification** | Two-sided read-back scoped to this service's own objects | The implemented checks were **switch-wide**: one matched any table at the stage with a port bind point, the other counted all entries against this service's rule count, with no clause tying an entry to this service's table. FR-100 generalises the obligation to every construct, keyed to that service's own objects. NFR-013 adds the control that would have caught it regardless of scoping: **a check counts only after it has been shown to FAIL on a stock fabric that does not carry the thing it checks for.** SC-040 measures the negative controls.
