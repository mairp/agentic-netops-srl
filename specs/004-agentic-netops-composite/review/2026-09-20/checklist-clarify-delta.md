## Scope and disclaimers

- **Nothing was ticked, edited, reordered or annotated.** The checklist file is unchanged; every one
  of its 40 items is still `[ ]`. This report is the only file written.
- This is **research for a decision, not the decision.** Where an item needs the operator, it is
  marked JUDGEMENT and the decision is named — it is not made here.
- Every claim about what the specification says carries a `file:line` citation. Where nothing could
  be found, the verdict says OPEN and names what was searched.
- **Timing matters**: the checklist was written *before* the fourth analysis pass
  (`spec.md:1766`–`1787`; `research.md` §13 `AD-23`…`AD-30`). Several items ask about text that pass
  has since changed; those are marked ANSWERED with the AD named.
- `AD-16`, `AD-17`, `AD-23`, `AD-26` and `AD-27` are recorded as **design choices the operator may
  reverse** (`spec.md:1751`, `spec.md:1770`), made on the analysis's own recommendation under a
  general "fix everything found" instruction. Any item whose answer rests on one of them is graded
  **JUDGEMENT at best**, however good the text now reads.

## Still open before implementation — ranked by risk

1. **CHK033 — a copied correlation label can adopt another service's claim** (OPEN). The adoption
   rule matches on label plus value only (`contracts/kuid-claim-profiles.md:180`) and nothing checks
   that the claim belongs to the adopting object. Two accepted objects could rest on one claim, and
   the first one's finalization would release an identifier the second still renders. This is the
   only item that describes a reachable correctness defect rather than a documentation gap.
2. **CHK002 — the open-finding consequence is not a requirement** (OPEN). It changes
   operator-visible acceptance behaviour (a render refused, a fabric reported degraded) and exists
   only in contracts. If the contracts are ever read as subordinate, an implementer may omit it.
3. **CHK006 / CHK034 — a re-verification that cannot run has no defined outcome** (OPEN). The
   dangerous default is that a read timeout flips `Ready=False`, which is exactly the "ambiguous
   success" inversion constitution Principle I guards against, in reverse. `VerificationFailed`
   exists as a reason code and is defined nowhere (`data-model.md:911` vs `data-model.md:917-943`).
4. **CHK035 — FR-106 (print the endpoint) and FR-079 (redact credentials) conflict** (OPEN). A
   base URL with embedded userinfo either leaks into every start-up log or is redacted into
   uselessness. Both are constitution-carried (CR-008, CR-005).
5. **CHK027 — four delta requirements have no success criterion and no recorded reason** (OPEN).
   FR-104, FR-106, FR-108 and NFR-014. Unmeasured requirements are what the inherited acceptance
   record was disputed over.
6. **CHK001 — force-release guard rules live only in contracts** (PARTIAL), while FR-075 grants the
   deployer `update` on service intent objects; the spec alone does not forbid the tier setting the
   annotation.
7. **CHK026 — FR-107's read load is absent from FR-086's session sizing** (OPEN). A session-limit
   exhaustion is already a listed edge case (`spec.md:598-599`).
8. **CHK008 — no orphan recovery for verification tooling that dies mid-write** (OPEN).
9. **CHK025 — no ordering between the audit export and operator-credential removal** (PARTIAL).
10. **CHK005 / CHK011 / CHK012 / CHK019 / CHK015 / CHK016** — wording gaps where a contract or the
    quickstart is more precise than the requirement it serves; low risk individually, but each is a
    place where an implementer reading only `spec.md` would guess.
