## 0. Bottom line up front

**SR Linux does not model the thing US3 is built on.** The blocker is not the containerised
dataplane and not the hardware gating — it is that **no SR Linux release through 26.7.2 has any
YANG for an explicit SRv6 segment list, an SRv6 policy, a steering entry, or a per-SID (MySID)
counter.** SR Linux SRv6 is *shortest-path SRv6 with BGP-signalled VPN service SIDs*, not
traffic-engineered SRv6. There is therefore no platform-neutral way to satisfy US3 acceptance
scenarios 2 and 3, FR-022's "bidirectional primary and alternate segment lists", FR-023's
"SRH presence, ordered SIDs … packet and byte counter increments … operator-directed path change",
or SC-009 — on *any* SR Linux platform, licensed or not, hardware or container.

On top of that, the license-free containerlab profile makes even the reduced outcome unreachable:

- On **25.10.3** the `/system/srv6` subtree **does not exist at all** on the 7220 IXR types I could
  boot (`ixr-d5`, `ixr-h5-64d`) `[VERIFIED: CLI probe, this session]`.
- On **26.7.2** it exists only on `ixr-h5-32d` / `ixr-h5-64d`, gated by a new feature
  `srv6-usid-basic`, and it exposes **only** a micro-SID block and a `uN` locator — no source
  address, no full-segment locator, no service SIDs, and **no `/network-instance/…/segment-routing`
  container at all** `[VERIFIED: gNMI + CLI schema tree, this session]`.
- Even that sliver is **accepted but not programmed**: `un value 100` is present in `running` and
  **absent from `state`**, with no route-table or tunnel-table entry
  `[VERIFIED: gNMI Set + CLI `info from running` vs `info from state`, this session]`.
- The chassis types (`ixr-x3b`, `sxr-1d-32d`, `ixr-h6`) **self-terminate ~60–75 s after boot without
  a license** `[VERIFIED: containerlab deploy, this session]`.
- Nokia's own 26.7 Segment Routing Guide closes the remaining door: **full SRv6 exists only on
  7730 SXR**; 7220 IXR-H5/H6 have "basic SRv6 support … pure transit nodes for uSID data traffic"
  with **"Service initiation or termination"** listed as *unsupported*; and **7250 IXR-6e/10e/X1b/X3b
  are not on the supported list at all** `[VERIFIED: documentation.nokia.com/srlinux/26-7/books/
  segment-routing/segment_routing_with_ipv6_data_plane_srv6.html]`. The only family that could host
  `SRv6Service`'s headend and egress is the one family that will not boot without a license.

**Recommendation: (d) demote behind a fail-closed capability gate — with the gate's content and the
service contract rewritten to the SR Linux-possible subset, and the impossible clauses explicitly
deferred to a future feature 005.** Runner-up: **(e) drop US3 to feature 005 and narrow the tier's
RBAC**. Detail and drafted wording in §6–§9.

## 3. Exactly what SR Linux models — and what it does not

### 3.1 Modelled (paths are gNMI paths; `[VERIFIED: YANG at tag v25.10.3 unless noted]`)

**System-level SRv6 (`srl_nokia-srv6.yang`, augments `/system`, `if-feature srv6` in 25.x; in 26.7.2
the guard is `if-feature "srl_nokia-feat:srv6 or srl_nokia-feat:srv6-usid-basic"`):**

```
/system/srv6                                        (presence container)
/system/srv6/source-address[ip-address=<ipv6>]      (max-elements 8)
/system/srv6/default-source-address                 (mandatory leafref, = SRv6 encap source)
/system/srv6/micro-segment/block-length             (range "32", default 32)
/system/srv6/micro-segment/sid-length               (range "16", default 16)
/system/srv6/micro-segment/gib-size                 (range "4..60", default 16 — × 1024 locators)
/system/srv6/micro-segment/block[block-name]/prefix/ip-prefix
/system/srv6/micro-segment/block[block-name]/static-function/max-entries  (1..1048575)
/system/srv6/locator[locator-name]                  (max-elements 16; name length 1..64, no '@')
/system/srv6/locator[locator-name]/full-segment/{block-length(0|64|96), function-length(16),
      argument-length(0|16, if-feature srv6-dt2), algorithm(0|128..255),
      prefix/ip-prefix, static-function/max-entries}
/system/srv6/locator[locator-name]/micro-segment/{block, argument-length, algorithm,
      un/srh-mode, un/value(1..1048575; 26.7.2: 1..65535)}
```

Constraints worth quoting: a locator `must` be exactly one of full-segment or micro-segment
(`"Full-segment and micro-segment cannot be configured togather"` — sic), and
`128 > argument-length + 2*sid-length + block-length`.

**Endpoint behaviours (`srl_nokia-srv6-instance.yang`, augments
`/network-instance/segment-routing`, `if-feature srv6`):**

```
/network-instance[name]/segment-routing/srv6/instance[id]           (id 1..2; only id=1 in "default")
  .../locator[locator-name]/full-segment/function/
        end[value]/srh-mode                 (netinst type MUST be "default"; max-elements 8)
        end-x[value]/{srh-mode, protection(unprotected|protected), subinterface-name}
        end-x-auto-allocate/{srh-mode, protection}
        end-dt4/value    end-dt6/value    end-dt46/value      (netinst type default or ip-vrf)
        end-dt2u/value   end-dt2m/value   (if-feature srv6-dt2; netinst type mac-vrf)
        end-dx2/value
  .../locator[locator-name]/micro-segment/function/
        ua[value]/{srh-mode, protection, subinterface-name}   ua-auto-allocate/{…}
        udt4/value  udt6/value  udt46/value  udt2u/value  udt2m/value  udx2/value
```

An SRv6 instance may only sit on a network-instance of type `default`, `ip-vrf`, `mac-vrf` or
`vpws`. `End`/`uN` transit lives in `default`; `End.DT46`/`uDT46` lives in the `ip-vrf` — which maps
cleanly onto `SRv6Service.spec.vrf`. `srh-mode` enum: `psp | usp | psp-usd | usp-usd | psp-usp-usd`
(`srl_nokia-srv6-types.yang`). Behaviour identities defined: `end, end-x, end-dt4, end-dt6,
end-dt46, end-dx2, end-dt2u, end-dt2m, un, ua, udt4, udt6, udt46, udx2, udt2u, udt2m`.

In 26.3.1+ the same module adds `config false` state: per-function `status` and `sid`
(`ipv6-prefix`, "The sid address associated with function"), `oper-value`, and locator/`un` `status`
`[VERIFIED: v26.7.2]`. In 25.7/25.10 the SRv6 modules contain **no `config false` node at all** —
there is no operational read-back of a SID in those releases `[VERIFIED: grep "config false" over
the three 25.10.3 SRv6 modules → zero hits]`.

**Service signalling:**

```
# BGP IP-VPN over SRv6 (srl_nokia-bgp-ipvpn.yang)
/network-instance[name]/protocols/bgp-ipvpn/bgp-instance[id]/encapsulation-type   enum {mpls, srv6}
/network-instance[name]/protocols/bgp-ipvpn/bgp-instance[id]/srv6/{default-locator, instance, source-address}
# BGP EVPN over SRv6 (srl_nokia-bgp-evpn.yang): same triple under the bgp-instance, plus
#   encapsulation-type enum value "srv6" and failure reasons
#   srv6_no_locator | srv6_no_source_address | srv6_no_sid
# Route policy can set the locator used for the BGP SRv6 TLV:
/routing-policy/policy[name]/statement[name]/actions/bgp/srv6/locator
```

**IGP:** `srl_nokia-srv6-isis.yang` augments
`/network-instance[name]/protocols/isis/instance[name]/segment-routing/srv6/{admin-state,
adj-sid-hold, locator[locator-name]/{level-capability, tag, multi-topology/*, level[level-number]/metric}}`
plus LSDB state for SRv6 Locator TLV, End SID, Adj-SID, SRv6 capabilities and MSD sub-TLVs.
**There is no OSPFv3 SRv6 module** `[VERIFIED: only `srl_nokia-srv6-isis.yang` exists]`, and every
IS-IS SRv6 augment is guarded `if-feature srl_nokia-feat:srv6` — so **locator advertisement in the
IGP requires IS-IS**. A BGP-only underlay cannot advertise a locator as an IGP locator; the locator
prefix is still an ordinary IPv6 prefix and could in principle be carried by BGP as a plain route,
but nothing in the model advertises the SRv6 Locator TLV over BGP `[VERIFIED: YANG; operational
behaviour UNVERIFIED]`. This is a direct conflict with the composite's BGP-unnumbered/eBGP underlay
assumption and means an SRv6 outcome drags IS-IS into the fabric design.

**Forwarding state (read-only), `srl_nokia-ip-route-tables.yang`:**

```
…/route-table/…/next-hop[index]/srv6-endpoint/{sid-value, behavior(identityref), locator-name, srh-mode, block-length}
…/next-hop[index]/srv6/tunnel/…
…/next-hop[index]/srv6-encapsulation/pushed-srv6-sid-stack  (leaf-list of ipv6-address)
…/next-hop[index]/srv6-encapsulation/source-address
```

`pushed-srv6-sid-stack` is the **only** place in the whole model where an ordered SID list appears —
and it is `config false` state describing what the resolver chose, not something an operator can set.

headend field deleted.

### 3.3 The SRH problem that the spec text does not anticipate

The task framing flagged this and it is correct, with a sharper edge:

- Under **uSID (micro-segment)** — the only flavour a license-free container exposes (§4) — up to
  six 16-bit uSIDs are carried **inside the 128-bit destination address of the outer IPv6 header**.
  A 2–3 hop path therefore produces **no SRH at all**, and `tcpdump … and srh` would capture
  nothing while the service works perfectly `[VERIFIED: model — `micro-segment/sid-length` range is
  fixed at 16 and `block-length` at 32, so a 128-bit carrier holds block + 6 uSIDs;
  UNVERIFIED: on-wire behaviour, never observed]`.
- Under **full-segment reduced encapsulation** with a shortest-path VPN service, the SID list is
  *one* SID (the egress `End.DT46`), and reduced encap puts that single SID in the destination
  address with **no SRH**.

So FR-023's "SRH presence, ordered SIDs" and SC-009's "capture-based ordered-SID, SRH …checks"
cannot be satisfied by a correct SR Linux SRv6 service. They are only satisfiable by a
traffic-engineered multi-SID path, which the platform cannot express. **This clause fails for a
reason unrelated to emulation: it fails on real hardware too.**

### 3.4 MTU arithmetic moves

The constitution's Network policy and `data-model.md` §20 state "SRv6 outer overhead is 40 bytes of
IPv6 header plus 8 bytes of SRH plus 16 per SID — approximately 96 bytes with 3 SIDs, leaving
approximately 9120" `[VERIFIED: /root/agentic-netops-srl/.specify/memory/constitution.md and
data-model.md §20]`. On SR Linux:

| Encapsulation | Overhead over 9216 underlay | Effective payload |
|---|---|---|
| uSID, ≤6 uSIDs in one carrier (the only license-free flavour) | 40 (outer IPv6 only, **no SRH**) | **9176** |
| Full-SID, reduced encap, 1 service SID (shortest-path L3VPN) | 40 | 9176 |
| Full-SID, reduced encap, 3 SIDs | 40 + 8 + 32 | 9136 |
| Full-SID, non-reduced, 3 SIDs (the number the spec uses) | 40 + 8 + 48 = 96 | 9120 |

`[VERIFIED: arithmetic; the encapsulation forms are from the model and RFC 8986 semantics,
UNVERIFIED on the wire]`. The spec's 9120 is the *worst* case and corresponds to an encapsulation
SR Linux never produces for a shortest-path service.

## 6. Alternatives assessed

### (a) SRv6 L3VPN best-effort on SR Linux (BGP-signalled `End.DT46`/`uDT46`, single SID, no explicit path)

The only SRv6 outcome the platform actually offers. Requires: `/system/srv6` locator +
`default-source-address`; `segment-routing/srv6/instance/.../udt46|end-dt46` in the tenant `ip-vrf`;
`bgp-ipvpn … encapsulation-type srv6` (or EVPN-IFL/VPWS with `srv6`); **IS-IS** with
`segment-routing/srv6/locator` for locator advertisement, because Nokia documents that *"the IS-IS
control plane only advertises the transport SID functions … SR Linux advertises service SID
functions in the BGP control plane only"* (§4.6) — which means adding IS-IS to a fabric the
composite otherwise runs on BGP. Costs: a **license** and a **7730 SXR** type — the only family with
full SRv6 (§4.6); no SXR container booted unlicensed here, and even licensed, the containerised
datapath's SRv6 forwarding is unproven (§4.4 shows the license-free sliver is not even programmed).
Note also that EVPN over SRv6 is limited to interface-less L3 and VPWS — *"MAC-VRF is not supported
in SR Linux"* over SRv6 — so this option cannot be folded into the existing `mac-vrf` construct.
Kills US3 scenarios 2 and 3 regardless.
**Verdict: technically the right target, but not reachable on the pinned license-free profile, and
it still fails half of FR-023 and all of SC-009's distinctive clauses.**

### (b) Linux/FRR endpoints doing `H.Encaps` with SR Linux as plain IPv6 transit

Would work — the Linux kernel's `seg6` does exactly this, and `/root/agentic-netops` already used
`ip -6 route … encap seg6 mode encap.red segs …` as a stand-in
`[VERIFIED: subagent report of tests/integration/evpn_srv6_suite.sh]`. It is also the one option
**the specification already forbids twice**: FR-001 ("All emulated network devices MUST be <NOS>
nodes") and, explicitly, `quickstart.md`: *"A failed SRv6 capability or packet-path check requires
another qualified profile; it cannot be replaced by mocked counters, **host-only SRv6**, or a
skipped acceptance test."* `[VERIFIED: /root/agentic-netops-srl/specs/004-agentic-netops-composite/
quickstart.md:602-603]`. Adopting it would require deleting that sentence — i.e. weakening the exact
anti-overclaim rule Principle I exists to enforce, in order to produce a green result that says
nothing about the NOS under test. **Reject.**

### (c) Mixed lab with a different NOS for SRv6

Violates FR-001 and re-opens the deny-list boundary (PC-20 / Open decision 6) in the worst possible
way: the retarget's whole point is a single-NOS fabric. Also doubles the image, licence and schema
surface for one user story. **Reject.**

### (d) Demote: keep the `SRv6Service` CRD and the requirements, behind a capability gate that fails
closed on the pinned profile (service reports `Ready=False`, feature reported unqualified, no
partial config)

This is the shape Principle VI prescribes for a gate that cannot hold. It preserves the CRD, the
allocation contract, the gate machinery, the RBAC grant and the option of qualifying a licensed
profile later, while making the *pinned* lab tell the truth. Its weakness: as written, US3/FR-023/
SC-009 would remain in the spec as requirements that are **unsatisfiable in principle** (not merely
unqualified on this profile) — which is itself a form of untruth. So (d) is only correct if the
impossible clauses are simultaneously rewritten or deferred (§7).

### (e) Drop US3 entirely to a future feature 005 and narrow the tier's RBAC (GAP-5)

Cleanest and smallest. Resolves GAP-5 by deletion (remove `srv6services` from the intent tier's
writer identity, so the vocabulary closure at four constructs and the RBAC grant finally agree),
removes eight requirement IDs' worth of unsatisfiable text, drops the topology from 8 nodes to 6,
and removes the SRv6 MTU arithmetic and the SRv6 telemetry/dashboard clauses. Its weakness: it
silently discards a *documented capability direction* (SRv6 L3VPN is real on SR Linux) and it
deletes the one requirement block that currently forces an IPv6 underlay (FR-003).

## 7. Recommendation

> **Adopt (d), scoped: keep `SRv6Service` and a fail-closed SRv6 capability gate, rewrite the
> gate's content and the service contract down to the SRv6 L3VPN subset SR Linux actually models
> (option (a)), and move every clause that SR Linux cannot express in any release —
> explicit two-path steering, SRH/ordered-SID capture, MySID counters, operator-directed path change
> — out of 004 into a deferred feature 005 rather than leaving them as requirements that cannot
> hold.**
>
> Runner-up if the team wants the smallest 004: **(e)**, with the deferral note below.

### Why this and not (e)

- **Principle VI is explicit about this exact situation**: *"A gate MUST NOT be waived to make a run
  pass; if a gate cannot hold, the limitation is documented and the affected service reports
  `Ready=False`."* `[VERIFIED: constitution.md:127-128]` That sentence describes (d) and nothing
  else. Deleting the user story is a legitimate scope decision, but it is *not* what the constitution
  says to do with a gate that cannot hold — it says report `Ready=False` and document.
- **Principle I forbids the other half of the status quo**: keeping FR-023/SC-009 as requirements
  while knowing no SR Linux release can satisfy them would be a specification-level overclaim, and
  the composite already has two recorded spec-vs-reality divergences; adding a third knowingly is
  worse than either (d) or (e). Hence the "rewrite/defer" half of the recommendation is not optional
  — (d) without it is **not** constitutionally clean.
- **The evidence in §4.4 is the argument in miniature**: SR Linux accepted the SRv6 write and did not
  program it. A system that reported `Ready=True` from the write alone would be exactly the false
  healthy Principle I's rationale describes. A fail-closed gate plus two-sided read-back catches it.
  That is a *demonstration of the platform's honesty*, and it is worth keeping the machinery that
  demonstrated it.
- **(e) throws away a working gate as well as a broken user story.** The capability-gate machinery
  (PC-N-11) is platform-neutral and is one of the composite's better ideas; SRv6 is its sharpest
  test case. Keeping one gate that legitimately fails closed on the pinned profile is cheap and
  proves the gate works.

### Why not (a) standalone, (b) or (c)

(a) alone still needs a license and a chassis type and still fails SC-009 — it is the *content* of
the rewritten gate, not an alternative to demotion. (b) and (c) are rejected in §6 on
FR-001/quickstart and single-NOS grounds respectively.

## 9. Drafted replacement wording

### 9.1 Under the recommendation — (d)-scoped

**US3 (replaces "User Story 3 — Provision and observe an end-to-end SRv6 service", priority P1 → P3):**

> ### User Story 3 — Qualify, and honestly refuse, an SRv6 VPN service (Priority: P3)
>
> A network engineer applies an `SRv6Service` connecting two IPv6 clients through an SRv6 L3VPN
> (locator, transit function, endpoint decapsulation into the service routed instance, BGP-signalled
> service SID). The platform first runs the SRv6 capability gate against the pinned profile. If any
> required capability is missing, the gate fails closed: the service reports `Ready=False` naming
> the missing capability, no device configuration is applied, no allocation is consumed, and the
> feature is reported unqualified on this profile. If a profile that passes the gate is available,
> the service converges and is verified by reading back the programmed locator, service SID and
> route state on both leaves.
>
> **Why this priority**: SRv6 on the pinned platform is release- and platform-gated and the
> license-free containerlab profile does not expose the required model. The user story's value in
> 004 is that it proves the capability gate fails closed rather than that it delivers an SRv6 data
> path. Traffic-engineered SRv6 — explicit segment lists, operator-selected paths and per-SID
> counters — is deferred to feature 005 because the target platform models none of them.
>
> **Independent Test**: apply one `SRv6Service` on the pinned profile. Observe: `Ready=False` with a
> condition naming each unmet capability; zero device configuration objects created; zero allocations
> claimed; a recorded gate report listing the capability, the path probed and the observed answer.
>
> **Acceptance Scenarios**:
> 1. **Given** the pinned profile, **When** the SRv6 gate runs, **Then** it reports, per capability,
>    the exact gNMI path probed and the observed result, and the run **fails** — it is never skipped
>    and never waived.
> 2. **Given** a failed gate, **When** an `SRv6Service` is applied, **Then** the controller sets
>    `Ready=False` with a reason naming the missing capability, creates no device configuration and
>    consumes no allocation, and no partial SRv6 configuration exists on any device.
> 3. **Given** a profile that passes the gate, **When** the service is applied, **Then** the
>    allocation authority issues collision-free IPv6 loopback, locator and function resources; the
>    controller renders locator, transit-function and endpoint-decapsulation configuration and the
>    BGP service encapsulation; and readiness is set only from device-observed state (locator and
>    SID `status`, the programmed service SID, and the SRv6 next-hop in the route table on both
>    leaves).
> 4. **Given** a converged service on such a profile, **When** IPv6 traffic runs between the two
>    clients, **Then** it passes bidirectionally through the service routed instance, is isolated
>    from other instances, and survives an MTU-sized acceptance packet.
> 5. **Given** any SRv6 capability that the platform does not model at all, **When** the gate runs,
>    **Then** it is reported as *unsupported by the platform* and is distinguished in the report from
>    *supported but failing*; neither is reported as a pass.

**FR-003 (rewritten):**

> - **FR-003**: All leaf-spine links and device loopbacks MUST have a qualified IPv6 underlay in
>   addition to the EVPN requirements. The SRv6 profile overlay, when enabled, MUST add
>   `srv6-client01` to `leaf01` and `srv6-client02` to `leaf02`; the default profile MUST NOT require
>   them.

**FR-005 (rewritten):**

> - **FR-005**: The SRv6 compatibility gate MUST verify, against the pinned image and schema:
>   IPv6 forwarding; the presence of the platform's SRv6 system model (locator, and either a
>   full-segment locator or a micro-segment block); a transit endpoint function; an endpoint
>   decapsulation function bound to a routed instance; BGP service signalling with SRv6
>   encapsulation; and the native SRv6 YANG paths over gNMI Set **and Get, with the written value
>   read back from operational state**. Each capability MUST be reported individually with the exact
>   path probed and the observed result. A capability the platform does not model MUST be reported
>   as unsupported, never as passed. Full acceptance MUST run on a profile that passes every check;
>   where no such profile exists, the gate MUST fail closed, the limitation MUST be documented, and
>   every dependent service MUST report `Ready=False`. Skipping, waiving, mocking a counter, or
>   substituting a host-only SRv6 implementation is forbidden.

**FR-021 (rewritten, second sentence unchanged):**

> - **FR-021**: The platform MUST define `SRv6Service.agentic-netops.io/v1alpha1`, because the pinned
>   upstream service API provides no locator, service-SID, behaviour or routed-instance binding
>   contract. Behaviour values MUST be restricted to those the pinned platform's schema defines
>   (a transit function and a routed-instance decapsulation function); a headend behaviour MUST NOT
>   be modelled as configuration, because the platform derives it from the service. The CRD MUST
>   reference existing topology, allocation and device-configuration resources rather than
>   duplicating their inventory, allocation or transaction responsibilities.

**FR-022 (rewritten):**

> - **FR-022**: Each SRv6 service MUST allocate unique locator and function resources through the
>   allocation authority, bind the endpoint decapsulation function to the correct routed instance,
>   render only schema-qualified device configuration paths, and claim nothing when the capability
>   gate has not passed.

**FR-023 (rewritten):**

> - **FR-023**: End-to-end SRv6 verification MUST prove, on a profile that passed the gate: client
>   IPv6 reachability in both directions through the service routed instance; the locator and
>   service SID present in device operational state on both endpoint leaves; an SRv6 next-hop for
>   the service prefix in the route table with the expected endpoint behaviour; routed-instance
>   isolation; and an MTU-sized acceptance packet. Where the platform carries the segment in the
>   destination address and emits no routing header, verification MUST record that fact rather than
>   assert the absence of an SRH as a failure.

**SC-009 (rewritten):**

> - **SC-009**: On the pinned profile the SRv6 capability gate fails closed in three consecutive
>   clean runs: every unmet capability is named with the path probed, no `SRv6Service` reaches
>   `Ready=True`, no device configuration object is created and no allocation is consumed. On a
>   profile that passes the gate, a bidirectional SRv6 L3VPN between the two IPv6 clients passes
>   traffic, read-back, isolation and MTU checks in three consecutive clean runs.

**SC-010 (rewritten):**

> - **SC-010**: Every SRv6 locator, service SID, endpoint behaviour and device configuration object
>   the platform models is visible in current-generation Kubernetes and device-configuration status,
>   and a configured object that does not appear in device operational state is reported as not
>   converged rather than as applied. A capability the platform does not model, or models but does
>   not program, fails before any partial service mutation and prevents aggregate `Ready`.

**New (carries the deferral explicitly, so nothing is lost silently):**

> - **FR-023a**: Traffic-engineered SRv6 — explicit segment lists, operator-selected primary and
>   alternate paths, capture-proven ordered SIDs in a routing header, and per-SID packet and byte
>   counters — is **deferred to feature 005**. The pinned platform models none of these in any
>   release through 26.7.2; this specification MUST NOT state them as requirements, and the
>   `SRv6Service` CRD MUST NOT carry a path-policy field that no reconciler can honour.

### 9.2 Under the runner-up — (e)

**US3**: deleted. Replaced in §User Stories by a one-paragraph note:

> **SRv6 (deferred to feature 005).** SRv6 was a first-class service outcome on the previous
> platform. The target platform documents SRv6 only from release 26.3.1 and only on 7730 SXR (full)
> and 7220 IXR-H5/H6 (uSID transit, explicitly incapable of service initiation or termination); the
> license-free containerlab types available to this lab expose either no SRv6 model at all or a
> transit stub that programs no SID; and no release through 26.7.2 models a segment list, steering
> entry, path policy or per-SID counter. Retaining the user story would mean
> carrying requirements no implementation could satisfy, which Principle I forbids. The user story,
> the `SRv6Service` CRD, its capability gate and its acceptance criteria move unchanged to feature
> 005, which must first qualify a licensed profile.

**FR-005**: deleted; the capability-gate existence requirement remains carried by FR-004 alone,
and FR-004 gains: *"The gate MUST report every checked capability individually, and a capability the
platform does not model MUST be reported as unsupported rather than passed."*

**FR-021, FR-022, FR-023**: deleted, with IDs retained as tombstones reading
*"Deferred to feature 005 — see §Deferred scope."*

**SC-009**: deleted (tombstone as above).

**SC-010 (rewritten to keep the platform-neutral half, which is about read-back, not about SRv6):**

> - **SC-010**: Every device configuration object a service creates is visible in current-generation
>   Kubernetes and device-configuration status; a configured object absent from device operational
>   state is reported as not converged; and an unsupported capability fails before partial service
>   mutation and prevents aggregate `Ready`.

**GAP-5 resolution clause (new, in §Cross-cutting gaps):**

> **[GAP-5] resolved**: the construct vocabulary stays closed at four constructs and the intent
> tier's writer identity no longer grants `srv6services`. The RBAC grant and the vocabulary now
> agree. Feature 005 re-opens the grant only together with a construct or an explicitly documented
> out-of-band operator path.

## 10. Residual unknowns, and what would change the answer

1. ~~Nokia's platform table~~ — **retrieved and folded into §4.6**. It did not soften the finding;
   it hardened it (7250 IXR-X/6e/10e have no SRv6; 7220 IXR-H5/H6 cannot initiate or terminate a
   service; only 7730 SXR is full-SRv6).
2. **A licensed 7730 SXR container** (`sxr-1d-32d`, `sxr-1x-44s`, `sxr-1-32d`) is the *only*
   remaining way to test whether SR Linux's XDP datapath encapsulates and decapsulates SRv6. If it
   does, option (a) becomes a real, qualifiable profile and the recommendation's §9.1 wording
   already accommodates it — scenario 3 of the rewritten US3 is exactly that case. Obtaining a
   license **and** an SXR-capable profile is therefore the single highest-value follow-up; note it
   also re-opens PC-03's question, because it means a second, licensed device profile in the lab.
   `[UNVERIFIED: whether SXR SRv6 forwards in the container — untestable on this host]`
3. **A later SR Linux release could add an SRv6 policy model.** The wording in §9.1 is written so
   that adding traffic-engineered SRv6 later is a feature-005 addition, not a contradiction of 004.
4. **If the team prefers (e)**, the only thing that must not be lost in the edit is FR-003's IPv6
   underlay obligation, which exists in the spec only because of SRv6 and which the IPv6 EVPN work
   and PC-17 still need.
