Minimal config, and the full key reference (all keys read from the `mapstructure` tags in
`pkg/outputs/otlp_output/otlp_output.go` **and** the doc table — they agree):

```yaml
outputs:
  otel:
    type: otlp                      # required
    endpoint: otel-collector.observability.svc.cluster.local:4317
    protocol: grpc                  # grpc | http   (default grpc; http → :4318 /v1/metrics)
    timeout: 10s                    # default 10s
    tls:                            # ca-file / cert-file / key-file / skip-verify
    batch-size: 1000                # default 1000
    interval: 5s                    # default 5s — max wait before flushing a non-empty batch
    buffer-size: 2000               # default 2 * batch-size
    compression: gzip               # http only; default gzip for http, ignored by grpc
    max-retries: 3                  # default 3
    metric-prefix: ""               # namespace prefix
    append-subscription-name: false # default false
    strip-leading-underscore: true  # default false — SEE §1.3, set this to true
    strings-as-attributes: false    # default false (string values dropped)
    resource-tag-keys: []           # default unset → ALL tags become data-point attributes
    counter-patterns: []            # regexes → matching values become monotonic cumulative Sums
    resource-attributes: {}         # static OTLP Resource attributes
    headers: {}                     # gRPC metadata / HTTP headers (redacted in logs)
    num-workers: 1                  # default 1
    debug: false
    enable-metrics: false           # exposes gnmic_otlp_output_* Prometheus metrics
    event-processors: []            # applied before OTLP conversion
```
`[VERIFIED: otlp_output.md configuration reference table + config struct lines 158–230 + setDefaultsFor lines 831–863]`

Transport detail worth recording: bare `host:port` + `protocol: http` becomes
`http://host:port/v1/metrics`; with a `tls` block it becomes `https://`. HTTP redirects are
**never followed** (treated as a permanent export failure) so the payload and the `headers`
(credentials) cannot be re-pointed at another origin.
`[VERIFIED: otlp_output.md "Transport" section]`

### 1.2 Recommendation: FR-089 stands as written — keep the single OTLP pipeline

```
SR Linux (gNMI :57400, json_ietf)
      │  stream/sample 5s, 13 subscriptions
      ▼
gnmic StatefulSet (in Kind, namespace observability)
      │  outputs.otel  type: otlp  protocol: grpc  →  :4317
      ▼
OpenTelemetry Collector (in-cluster)
      receivers:  otlp/grpc (devices), otlp (agent tier fan-in per D-37)
      processors: filter/metrics (name allow-list per D-37), memory_limiter, batch
      exporters:  prometheus (:8889 /metrics, pull)
      ▼
Prometheus (in-cluster) ── scrape job "otel-collector" + job "gnmic-self" (:7890/metrics)
      ▼
Grafana (in-cluster, provisioned datasource + dashboards + pinned plugin)
```

The conforming alternatives, and why they lose:

| Option | FR-089 "single collector pipeline" | FR-088 "collector does not store" | Verdict |
|---|---|---|---|
| **A. gnmic `otlp` → collector `otlp` receiver → `prometheus` exporter → Prometheus scrape** | Honest: one collector, one pipeline | Honest: exporter is a stateless exposition surface with `metric_expiration` (default 5m) | **Recommended** |
| B. gnmic `prometheus` output (`:9273`) → collector `prometheusreceiver` scrapes gnmic → `prometheus` exporter → Prometheus scrape | Two scrape hops; the collector becomes a *relay of a scrape*, which reads as two pipelines in runtime inspection (SC-037) | Same | Rejected — SC-037 becomes hard to prove |
| C. gnmic `prometheus_write` output → collector `prometheusremotewritereceiver` → `prometheusremotewrite` exporter → Prometheus | Works; loses OTLP resource semantics; needs Prometheus `--web.enable-remote-write-receiver` | Same | Rejected — extra moving part, no benefit now that `otlp` exists |
| D. gnmic `prometheus` output scraped by Prometheus **directly** (what the reference lab does) | **Non-conforming** — there is no collector in the device path at all | n/a | Rejected. This is what `srl-telemetry-lab` does `[VERIFIED: configs/prometheus/prometheus.yml scrapes gnmic:9273 directly]` — it is the exact pattern FR-089 was written to forbid. |

Note on the exporter side: the collector's `prometheus` exporter is a **pull** exposition
endpoint with `metric_expiration` (default `5m`), `namespace`, `const_labels`,
`send_timestamps`, `enable_open_metrics`, `add_metric_suffixes` (default true, deprecated in
favour of `translation_strategy`), and resource attributes go to a `target_info` metric unless
`resource_to_telemetry_conversion` (deprecated) / `resource_constant_labels` is used.
`[VERIFIED: opentelemetry-collector-contrib/exporter/prometheusexporter/README.md]`

**Pin `add_metric_suffixes: false`** (or `translation_strategy: UnderscoreEscapingWithoutSuffixes`).
Otherwise every metric classified as a Sum by `counter-patterns` gains a `_total` suffix and the
generated dashboards / flow-panel `dataRef`s silently stop matching. This is a
requirement-relevant pin, not a taste call — see §1.3.

### 1.3 Metric naming under OTLP vs under the prometheus output — the one real trap

gnmic builds an OTLP metric name from `metric-prefix` + optional subscription name + the gNMI
**value path** with `/` and `-` replaced by `_`. By default the leading `/` becomes a leading
`_`, producing `__interface_traffic_rate_in_bps`-style names; `strip-leading-underscore: true`
elides it. `[VERIFIED: otlp_output.md "Metric Names"]`

The gnmic **prometheus** output (what every published SR Linux lab uses) joins prefix,
subscription name and key-stripped path with single underscores and replaces all
non-alphanumerics with `_`. `[VERIFIED: prometheus_output.md "Metric Naming"]`

So with `metric-prefix: ""`, `append-subscription-name: false`, `strip-leading-underscore: true`,
the OTLP pipeline reproduces **exactly** the metric names the published dashboards use:

| gNMI value path | Metric name | Seen in a real dashboard? |
|---|---|---|
| `/interface/oper-state` | `interface_oper_state` | yes `[VERIFIED: telemetry-dashboard.json flow panel target A]` |
| `/interface/traffic-rate/in-bps` | `interface_traffic_rate_in_bps` | yes `[VERIFIED: same]` |
| `/network-instance/route-table/ipv4-unicast/statistics/active-routes` | `network_instance_route_table_ipv4_unicast_statistics_active_routes` | yes `[VERIFIED: same, "Routing Stats" panel]` |
| `/platform/control/cpu/total/instant` | `platform_control_cpu_total_instant` | yes `[VERIFIED: same, "CPU Utilization"]` |
| `/platform/control/memory/utilization` | `platform_control_memory_utilization` | yes |
| `/network-instance/protocols/bgp/statistics/up-peers` | `network_instance_protocols_bgp_statistics_up_peers` | yes |
| `/system/app-management/application/pid` | `system_app_management_application_pid` | yes |

That equivalence is *the* reason to keep FR-089 as written: the OTLP route costs nothing in
dashboard portability.

### 1.4 Label (attribute) derivation — exact rules

gnmic derives a tag per gNMI path key as `<last path element name>_<key name>`, verbatim,
including hyphens:

```go
elems := strings.Split(e.Name, ":")
ksb.WriteString(elems[len(elems)-1]); ksb.WriteString("_"); ksb.WriteString(k)
tags[ksb.String()] = v
```
`[VERIFIED: gnmic v0.47.0 pkg/formatters/event.go, tagsFromGNMIPath(), lines ~196–216]`

and the `source` tag is the **target name** (`t.Config.Name`), not the address:

```go
m := outputs.Meta{"source": t.Config.Name, "format": ..., "subscription-name": sreq.name}
```
`[VERIFIED: pkg/app/gnmi_client_subscribe.go:301 and pkg/app/subscribe.go:274]`
and a target's `name` defaults to the target map key but can be set explicitly
`[VERIFIED: docs/user_guide/targets/targets.md lines 208–219]`.

**Consequence (requirement-relevant):** name every gnmic target with the **containerlab node
name** and give it an explicit `address:` —

```yaml
targets:
  leaf1: { name: leaf1, address: clab-fabric-leaf1:57400, ... }
```

otherwise `source` becomes `10.x.y.z:57400` and the FR-094 topology join breaks. This is the
identifier contract PC-A-09 refers to; it must be stated, not assumed.

Raw tag names and their Prometheus-sanitised forms:

**Do not rely on the exporter's sanitiser.** Under the prometheus *output* the sanitisation is
gnmic's own and is stable; under OTLP the sanitisation happens in the collector's prometheus
exporter and is governed by `translation_strategy`, which is a moving target. Normalise at the
source with an `event-strings` tag-name transform, and **record path → metric name → label names
in the path register (FR-017)**. That makes the flow-panel join a specified contract.

### 1.5 gnmic in Kubernetes

Three deployment shapes, in increasing order of machinery:

1. **Single-replica StatefulSet + ConfigMap** (recommended for this 4-node lab). Config and
   targets in a ConfigMap; `api-server.enable-metrics: true` exposes `/metrics` and `healthz`
   for probes `[VERIFIED: gnmic-src/docs/user_guide/api/api_intro.md lines 30–68]`.
2. **File target loader over a mounted ConfigMap** — `loader: {type: file, path: …, interval: 30s}`.
   "Newly added targets are discovered and subscribed to. Deleted targets are removed from
   gNMIc's list and their subscriptions are terminated."
   `[VERIFIED: docs/user_guide/targets/target_discovery/file_discovery.md]`
   This is the K8s-native way to make FR-096's provisioning script and the fabric inventory the
   single source of truth: the same generator that writes the topology metadata writes the
   targets file. **There is no Kubernetes target loader**: the loader set is
   `consul_loader, docker_loader, file_loader, http_loader`
   `[VERIFIED: gnmic-src/pkg/loaders/ directory listing]`.
3. **Clustering** for HA — leader election and target lock/distribution via a Consul locker,
   `clustering: {cluster-name, instance-name, services-watch-timer 60s, targets-watch-timer 20s,
   target-assignment-timeout 10s, leader-wait-timer 5s, tags}`
   `[VERIFIED: docs/user_guide/HA.md]`. The upstream Kubernetes example is a 3-instance
   StatefulSet + headless Service + Consul + a Prometheus-Operator `ServiceMonitor`
   `[VERIFIED: docs/deployments/clusters/kubernetes/cluster_with_prometheus_output.md]`.

There **is** a gNMIc Operator: `github.com/gnmic/operator`, Apache-2.0, latest **v0.5.0**, API
group `v1alpha1`, CRDs `Cluster, Pipeline, Target, TargetSource, TargetProfile,
TunnelTargetPolicy, Subscription, Output, Input, Processor`, installed via
`helm install gnmic-operator oci://ghcr.io/gnmic/operator/charts/gnmic-operator`
`[VERIFIED: WebFetch github.com/gnmic/operator]`. Whether it supports `type: otlp` outputs is
**not stated in its docs** `[UNVERIFIED]`.

**Recommendation:** shape 1 + shape 2 (StatefulSet + file loader). Reject the operator for now —
`v0.5.0`/`v1alpha1` on a platform whose NFR-003 forbids unpinned or unstable dependencies is a
liability, and it adds a CRD surface that duplicates what a 40-line ConfigMap already expresses.
Record it as the documented scale-out path. Reject Consul clustering: one gnmic replica covering
4 devices is not a redundancy problem worth a KV store, and Consul would be a second
state-holding workload that FR-088's "the collector stores nothing" discipline has to explain.

### 2.2 Enum handling: `session-state` and `oper-state`

`session-state` is an enumeration with explicit values:

```yang
leaf session-state { config false; type enumeration {
  enum idle {value 0;} enum connect {value 1;} enum active {value 2;}
  enum opensent {value 3;} enum openconfirm {value 4;} enum established {value 5;} } }
```
`[VERIFIED: srlinux-yang-models v25.10.3 srl_nokia-bgp.yang lines 1517–1542]`

With `json_ietf` encoding the wire value is the **enum name string** (`"established"`), not the
integer. Two ways to make it a metric:

- **(recommended)** `event-strings` value replacement to an integer, the same trick both Nokia
  labs use for `oper-state`:
  ```yaml
  processors:
    bgp-session-state-to-int:
      event-strings:
        value-names: [".*session-state$"]
        transforms:
          - replace: {apply-on: value, old: "^established$", new: "5"}
          - replace: {apply-on: value, old: "^openconfirm$", new: "4"}
          - replace: {apply-on: value, old: "^opensent$",   new: "3"}
          - replace: {apply-on: value, old: "^active$",     new: "2"}
          - replace: {apply-on: value, old: "^connect$",    new: "1"}
          - replace: {apply-on: value, old: "^idle$",       new: "0"}
  ```
  giving `network_instance_protocols_bgp_neighbor_session_state == 5` for healthy.
- **(alternative)** set `strings-as-attributes: true` on the OTLP output: string values become
  gauges with value `1` and the string in a `value` attribute
  `[VERIFIED: otlp_output.md "Metric Names" / config comment]`. Rejected: it makes alert
  expressions `{value!="established"}`, i.e. the alert becomes a label-match rather than a
  numeric threshold, and it silently multiplies series.

`oper-state` is handled identically; both published labs use:
```yaml
oper-state-to-int:
  event-strings:
    value-names: [".*"]
    transforms:
      - replace: {apply-on: value, old: "up",   new: "1"}
      - replace: {apply-on: value, old: "down", new: "0"}
```
`[VERIFIED: srl-telemetry-lab/configs/gnmic/gnmic-config.yml and srl-sros-telemetry-lab/gnmic-config.yml]`
Caution: as written that transform applies to **every** value name and will corrupt any string
value containing `up`/`down` (e.g. `oper-down-reason`). Scope `value-names` to
`["oper-state$", "admin-state$", "state$"]` rather than `".*"`. This is a real defect in the
reference config, inherited by anyone who copies it.

### 2.3 Event processors — the full recommended set

```yaml
processors:
  # 1) containerlab-compatible interface names: ethernet-1/49 -> e1-49
  rename-srl-interface:
    event-strings:
      tag-names: ["^interface_name$"]
      transforms:
        - replace: {apply-on: value, old: "ethernet-(\\d+)/(\\d+)", new: "e$1-$2"}

  # 2) Prometheus-clean label names at the source (do not rely on the exporter)
  clean-label-names:
    event-strings:
      tag-names: [".*-.*"]
      transforms:
        - replace: {apply-on: name, old: "-", new: "_"}

  # 3) shorten the afi-safi label
  rename-afi-safi:
    event-strings:
      tag-names: ["^afi_safi_afi_safi_name$"]
      transforms:
        - replace: {apply-on: name, old: "afi_safi_afi_safi_name", new: "afi_safi"}

  # 4) numeric state
  oper-state-to-int:  { ... as above, scoped value-names ... }
  bgp-session-state-to-int: { ... }

  # 5) drop the high-churn / useless tags before they become labels
  drop-noise:
    event-delete:
      tag-names: ["^subscription-name$"]
```
`[VERIFIED: processor families exist — gnmic-src/docs/user_guide/event_processors/ lists
event_strings, event_delete, event_add_tag, event_value_tag, event_to_tag, event_convert,
event_jq, event_starlark, event_group_by, event_allow, event_drop, event_rate_limit, …]`
`[VERIFIED: rename-srl-interface pattern is verbatim from srl-telemetry-lab/configs/gnmic/gnmic-config.yml]`

The `trim-prefixes` processor in the reference lab (trimming `^/state/`) is **vestigial for SR
Linux** — SR Linux native paths have no `/state/` prefix; it exists because the sibling lab also
collects SR OS, whose paths do (`/state/port[port-id=*]/…`).
`[VERIFIED: srl-sros-telemetry-lab/gnmic-config.yml SROS paths all begin /state/]`
Do not copy it.

### 2.4 Encoding, `updates-only`, on-change, and server limits

- **Encoding.** Use `encoding: json_ietf` explicitly. SR Linux's Capabilities response advertises
  **JSON_IETF, ASCII, PROTO** `[VERIFIED: documentation.nokia.com/srlinux/25-10/books/system-mgmt/gnmi.html]`;
  gnmic's default is plain `json` `[VERIFIED: gnmic --help, -e default "json"]`. The sibling lab
  sets `encoding: json_ietf` explicitly `[VERIFIED: srl-sros-telemetry-lab/gnmic-config.yml]`;
  `srl-telemetry-lab` omits it `[VERIFIED: its gnmic-config.yml has no encoding key]`. Set it.
  With `json_ietf` SR Linux returns a subtree as one JSON blob per update and gnmic flattens it
  into many values on one event — which is why subscribing to `…/statistics` (a container) is
  idiomatic and cheap.
- **`proto` encoding** yields one leaf update per value. Lower per-message parse cost, but the
  event stream and therefore metric names are identical. No reason to prefer it here. `[UNVERIFIED:
  relative performance on SR Linux]`
- **`updates-only`.** gnmic supports it per subscription ("the target MUST not transmit the
  current state of the paths that the client has subscribed to, but rather should send only
  updates to them") `[VERIFIED: gnmic-src/docs/user_guide/subscriptions.md lines 72–74]`.
  Whether SR Linux 25.10 honours it is **not documented in the pages read**
  `[UNVERIFIED]`. **Recommendation: leave `updates-only` false.** The initial sync is what makes
  the dashboards correct immediately after a gnmic restart, which SC-034 ("dashboards load …
  without manual setup") depends on.
- **`suppress-redundant` + `heartbeat-interval`.** Supported per subscription
  `[VERIFIED: subscriptions.md lines 67–71]`. Useful for the `sample`-mode state subscriptions
  (1, 5, 8) if on-change is unavailable: suppress identical samples, but heartbeat every 60s so
  Prometheus staleness does not fire. **Recommended for subscriptions 1, 5, 8.**
- **On-change.** SR Linux documents ON_CHANGE, SAMPLE, TARGET_DEFINED and POLL, with
  TARGET_DEFINED described as "the target dictates the ideal subscription type … for each leaf …
  if the path refers to leaves that are event-driven, then an ON_CHANGE subscription may be
  created" `[VERIFIED: documentation.nokia.com/srlinux/25-10/books/system-mgmt/gnmi.html]`.
  **There is no published per-path on-change support matrix** `[UNVERIFIED]`, and *both* Nokia
  reference labs use `stream-mode: sample` for **every** subscription including `oper-state` and
  `network-instance/oper-state` `[VERIFIED: both gnmic-config.yml files]`. That is strong
  evidence that `sample` is the safe default.
  **Recommendation:** default everything to `sample`; add `on-change` for subscriptions 1, 5 and
  8 **only behind a validated acceptance check** (subscribe, bounce a link, confirm an update
  arrives within 2s). Use gnmic's `stream-subscriptions` list to mix modes inside one Subscribe
  RPC `[VERIFIED: subscriptions.md lines 81–94]`.
- **Server limits.** SR Linux `system grpc-server <name>` exposes `rate-limit` (RPC calls per
  minute), `session-limit` (max simultaneous gRPC sessions), `max-concurrent-streams`, `timeout`,
  `port` (default **57400**), `network-instance` (default `mgmt`), `services [gnmi gnoi gnsi
  gribi p4rt]`, `tls-profile`, `metadata-authentication`, `yang-models`
  `[VERIFIED: documentation.nokia.com/srlinux/25-10/books/config-basics/management-servers.html]`.
  **Requirement-relevant:** the device-configuration layer (sdcio) and gnmic are two independent
  gRPC clients against the same server. `session-limit` and `max-concurrent-streams` must be
  sized for both, and the value must be pinned in the device baseline config — otherwise a
  gnmic reconnect storm can starve the config plane. Non-default ports additionally require a
  CPM/ACL filter entry `[VERIFIED: same page]`.
- Subscriptions cannot be modified once established; a new Subscribe RPC is required for new
  paths `[VERIFIED: Nokia Subscribe RPC doc]`. So a change to the path register is a gnmic
  config reload + resubscribe, not a hot edit. Worth saying in FR-017's wording.

## 3. OpenConfig telemetry on SR Linux — recommend **native**

**Status.** OpenConfig is supported and is enabled with
`system management openconfig admin-state enable`; the gRPC server selects the schema with
`system grpc-server <name> yang-models openconfig`, or a client sets `origin: "openconfig"` in
the request. `[VERIFIED: documentation.nokia.com/srlinux/25-10/books/system-mgmt/yang-data-models.html]`
The OC modules ship in the models repo under `openconfig/` (acl, aft, bfd, bgp, interfaces, isis,
lacp, lldp, mpls, network-instance, platform, policy, qos, rib, segment-routing, system, vlan, …)
together with `openconfig-srl-deviations.yang` and `openconfig-srl-augments.yang`
`[VERIFIED: srlinux-yang-models v25.10.3 directory listing]`, and the **OC↔native mapping files**
are shipped as JSON in `mappings/openconfig/` (`oc-srl-interface.json`,
`oc-srl-network-instance.json`, `oc-srl-bgp.json`, `oc-srl-platform.json`, `oc-srl-acl.json`,
`oc-srl-unsupported.json`, …) `[VERIFIED: same]`. On the device they live in
`/opt/srlinux/mappings/openconfig/` `[VERIFIED: Nokia yang-data-models page]`.

**Coverage, measured from those mapping files** (an entry with `"supported": false` is a path the
mapping explicitly does not implement):

| Mapping file | entries | explicitly unsupported |
|---|---:|---:|
| `oc-srl-interface.json` | 269 | 92 |
| `oc-srl-network-instance.json` | 994 | **826** |
| `oc-srl-bgp.json` | 652 | 193 |
| `oc-srl-platform.json` | 316 | 167 |

`[VERIFIED: computed this session from srlinux-yang-models v25.10.3 mappings/openconfig/*.json]`

And the decisive one — `oc-srl-unsupported.json`:

```json
{"oc": "/network-instances/network-instance/evpn",  "supported": false}
{"oc": "/network-instances/network-instance/vlans", "supported": false}
{"oc": "/network-instances/network-instance/protocols/protocol/segment-routing", "supported": false}
{"oc": "/network-instances/network-instance/protocols/protocol/mpls",  "supported": false}
{"oc": "/network-instances/network-instance/protocols/protocol/ospfv2","supported": false}
{"oc": "/keychains", "supported": false}
```
`[VERIFIED: srlinux-yang-models v25.10.3 mappings/openconfig/oc-srl-unsupported.json]`

Interface counters **do** map cleanly
(`/interfaces/interface/state/counters/in-octets → /interface/statistics/in-octets`, and 17 more)
`[VERIFIED: oc-srl-interface.json]`, but there is **no OpenConfig path for SR Linux's
`traffic-rate/{in,out}-bps`** — that leaf has no OC counterpart, so the flow panel's headline
signal would have to be reconstructed with `rate()` over `in-octets` at the query layer.

**Recommendation — native (`srl_nokia`) for all telemetry.** Reasons, in order:
1. EVPN — the platform's entire overlay story — is explicitly **unsupported** in the OC mapping.
   PC-A-08's EVPN paths simply do not exist in OC on this NOS.
2. `traffic-rate` has no OC equivalent; every published SR Linux weathermap is built on it.
3. Native is the "no translation layer" path Nokia itself markets for streaming telemetry, and
   both Nokia reference labs subscribe natively `[VERIFIED: both gnmic-config.yml files]`.
4. The device-configuration layer (sdcio) and the intent tier already work against a
   native-schema device model; a second schema on the telemetry side would fork the path register.

**Consistency with FR-017 (path register).** State the register as schema-qualified:

> The path register MUST record, for every subscribed leaf: the gNMI `origin` (`srl_nokia` — the
> default native origin), the xpath with its list keys, the subscription name and stream mode,
> the derived Prometheus metric name, the derived label names, the SR Linux release the entry was
> validated against, and whether the leaf is an enumeration requiring a value transform.
> Registering a path under the `openconfig` origin MUST be accompanied by a recorded check
> against `/opt/srlinux/mappings/openconfig/` that the path is not marked `"supported": false`.

That last clause is the cheap, verifiable guard that keeps a future OC excursion from silently
producing empty panels.

   containerlab metadata" becomes a test rather than an assertion.

## 5. Resolving Open decision 6 / PC-20 / SC-017(b)

### 5.1 What the clause says today

> **SC-017** … (b) *Visualization boundary* (FR-094): no runtime artifact of the published
> telemetry lab's network operating system in the dependency graph; that repository may be cited
> as a visualization pattern only.
`[VERIFIED: spec.md lines ~1110–1118]`

> **FR-094** … The published telemetry lab this exposition pattern is drawn from is a
> **visualization reference only**; no runtime artifact of that lab's network operating system
> may enter the dependency graph.
`[VERIFIED: spec.md lines 925–930]`

Under the retarget, "that lab's network operating system" *is* SR Linux, and SR Linux is the
target runtime. The clause forbids the deliverable. It must change.

### 5.2 What the clause was actually protecting

Read against D-36 and the placement boundary (c), the original intent decomposes into three
distinct protections, only one of which was about the NOS:

1. **Don't adopt a second NOS as a runtime just because you borrowed its dashboards.** — Dead.
   The NOS is now the target.
2. **Don't take a runtime dependency on a third-party lab repository's artefacts.** — Alive, and
   §4.1 shows it is a *live, unpinned, internet-egress* risk: the reference dashboard fetches
   `panelConfig`, `siteConfig` and `svg` from `raw.githubusercontent.com/.../main/...` at panel
   render time `[VERIFIED: telemetry-dashboard.json]`, and installs its Grafana plugin unpinned
   `[VERIFIED: st.clab.yml]`. This is precisely an NFR-003 violation wearing a visualization hat.
3. **Don't adopt that lab's deployment shape.** — Alive but **already covered by boundary (c)**:
   the lab runs gnmic, Prometheus, Grafana, Alloy and Loki as containerlab `linux` nodes, i.e.
   Docker containers outside Kubernetes `[VERIFIED: st.clab.yml TELEMETRY STACK / LOGGING STACK
   node definitions]`. Boundary (c) ("no Compose or outside-Kubernetes deployment of platform
   applications") forbids that already.

So: protection 1 is obsolete, protection 3 is duplicated, protection 2 is real, unduplicated and
now *more* important than before (because the retarget makes copying from that repo attractive).

### 5.3 Options and consequences

| Option | What it does | Consequence |
|---|---|---|
| **(i) Drop (b) entirely** | SC-017 becomes two boundaries | Loses protection 2 outright; renumbers (c)→(b), breaking traceability.md rows and the PC-21 sibling framing; the deny-list CI job loses the only rule that catches `raw.githubusercontent.com` in a dashboard JSON. **Rejected.** |
| **(ii) Re-scope to a reference-artifact provenance boundary** | (b) forbids *runtime* dependency on the reference lab repository — its images, its branch-served config/SVG/dashboard URLs, its unpinned plugin installs — while explicitly *permitting* reuse of its patterns and of pinned, vendored copies of its artefacts | Keeps three boundaries and all numbering; turns a now-incoherent rule into a rule with a real, mechanically checkable violation (`grep raw.githubusercontent.com`, `grep GF_INSTALL_PLUGINS` without a version, unpinned `--drawio-version`); is honest about the retarget. **Recommended.** |
| **(iii) Re-scope to forbid Compose/host-side telemetry stacks** | (b) becomes "no telemetry component outside the cluster" | Pure duplication of (c). Two boundaries with the same predicate makes the deny-list incoherent in a different way. **Rejected.** |
| **(iv) Replace with a "not this" boundary against some other NOS** | e.g. forbid SONiC runtime artifacts | Inverts the problem again on the next retarget and encodes an arbitrary grudge. **Rejected.** |

### 5.4 Recommended replacement text

**FR-094 — replace the last sentence** (from "The published telemetry lab …" to the end):

> The published telemetry lab whose exposition pattern this view is drawn from is a
> **visualization and generator reference only**. Its panel schema, cell-identifier convention,
> metric-to-cell join contract and topology-generator tooling MAY be reused. Every reused

**Recommendation: keep durable logs out of scope, as FR-088 already says.** Reasons:
1. FR-088 is explicit: "Durable logs and traces are out of scope unless a log store and a trace

2. No success criterion requires logs. SC-034/035/036/037 are all metric-shaped.
3. It would double the observability namespace's footprint for a lab whose device count is four.

**But record two things in the plan**, so the decision is reversible at low cost:
- the syslog→`source` relabel contract above, so a later Loki addition joins to the same key and

- a note that if logs are ever added, `alloy` replaces `promtail` (the lab migrated:

## 7. Alerts (SC-035, SC-037)

Metric names below are exactly those the §1/§2 pipeline produces (`metric-prefix: ""`,
`append-subscription-name: false`, `strip-leading-underscore: true`,
`add_metric_suffixes: false`). `interface_oper_state` / `network_instance_oper_state` are 1/0 and
`…bgp_neighbor_session_state` is 0–5 after the §2.2 transforms.

```yaml
groups:
  - name: fabric-underlay
    rules:
      # SC-035: link down
      - alert: FabricLinkDown
        expr: interface_oper_state{interface_name=~"e1-.*"} == 0
        for: 30s
        labels: {severity: critical, boundary: underlay}
        annotations:
          summary: "{{ $labels.source }} {{ $labels.interface_name }} is operationally down"

      - alert: FabricLinkFlapping
        expr: increase(interface_statistics_carrier_transitions[10m]) > 4
        for: 0m
        labels: {severity: warning}

      - alert: FabricLinkErrors
        expr: rate(interface_statistics_in_error_packets[5m])
              + rate(interface_statistics_in_discarded_packets[5m]) > 0
        for: 2m
        labels: {severity: warning}

      # SC-035: BGP session down  (5 == established)
      - alert: BGPSessionDown
        expr: network_instance_protocols_bgp_neighbor_session_state != 5
        for: 60s
        labels: {severity: critical}
        annotations:
          summary: "BGP {{ $labels.source }} → {{ $labels.neighbor_peer_address }} in state {{ $value }} (ni={{ $labels.network_instance_name }})"

      # cheap cross-check that survives an enum rename
      - alert: BGPPeerCountMismatch
        expr: network_instance_protocols_bgp_statistics_up_peers
              < network_instance_protocols_bgp_statistics_total_peers
        for: 60s
        labels: {severity: critical}

  - name: fabric-overlay
    rules:
      - alert: ServiceInstanceDown              # mac-vrf / ip-vrf
        expr: network_instance_oper_state{network_instance_name!="mgmt"} == 0
        for: 60s
        labels: {severity: critical}

      # Superseded 2026-09-20 by AD-31 (research.md §13; review/2026-09-20/AD-23-fabric-readiness.md).
      # As drafted below this rule fires on every node from three minutes after FabricReady until
      # the first service spans two leaves, and again after the last one is deleted — which is
      # exactly the state AD-23 declares correct. The shipped rule MUST be guarded on the presence
      # of at least one bgp-evpn bgp-instance on that source; the guard series name comes from the
      # collector naming qualified alongside G7, not from this draft. The requirement lives in
      # tasks.md T130, quickstart.md §21 and plan.md R-46; this block is research, not design.
      - alert: EvpnRoutesLost
        expr: network_instance_protocols_bgp_neighbor_afi_safi_received_routes{afi_safi="evpn"} == 0
              and on(source) network_instance_protocols_bgp_neighbor_session_state == 5
        for: 3m
        labels: {severity: warning}

      - alert: VtepSilent                        # no VXLAN traffic from a known peer VTEP
        expr: rate(tunnel_vxlan_tunnel_vtep_statistics_in_packets[5m]) == 0
        for: 10m
        labels: {severity: warning}
        annotations:
          summary: "No ingress VXLAN packets from VTEP {{ $labels.vtep_address }} at {{ $labels.source }}"

      - alert: VxlanDiscards
        expr: rate(tunnel_vxlan_tunnel_vtep_statistics_in_discarded_packets[5m]) > 0
        for: 5m
        labels: {severity: warning}

      - alert: MacTableNearLimit
        expr: network_instance_bridge_table_statistics_total_entries
              / on(source, network_instance_name)
              network_instance_bridge_table_mac_limit_maximum_entries > 0.9
        for: 5m
        labels: {severity: warning}

  - name: telemetry-pipeline          # SC-037
    rules:
      # stage 1: gnmic ↔ device
      - alert: DeviceTelemetryTargetDown
        expr: gnmic_target_up == 0
        for: 60s
        labels: {severity: critical, stage: "gnmic-subscribe"}

      - alert: DeviceSubscriptionStalled
        expr: rate(gnmic_subscribe_number_of_received_subscribe_response_messages_total[5m]) == 0
        for: 3m
        labels: {severity: critical, stage: "gnmic-subscribe"}

      # stage 2: gnmic → OTel collector
      - alert: OtlpExportFailing
        expr: rate(gnmic_otlp_output_number_of_failed_events_total[5m]) > 0
        for: 2m
        labels: {severity: critical, stage: "gnmic-otlp-export"}

      - alert: OtlpDataPointsRejected
        expr: rate(gnmic_otlp_output_rejected_data_points_total[5m]) > 0
        for: 2m
        labels: {severity: critical, stage: "otel-collector-ingest"}
        annotations:
          description: "PartialSuccess rejections are NOT retried; a fully rejected batch still counts as sent."

      # stage 3: collector → Prometheus
      - alert: DeviceMetricsAbsent
        expr: absent(interface_traffic_rate_in_bps)
        for: 2m
        labels: {severity: critical, stage: "prometheus-scrape"}

      - alert: ObservabilityTargetDown          # SC-034
        expr: up{job=~"otel-collector|gnmic-self|provider|sdc|prometheus"} == 0
        for: 60s
        labels: {severity: critical}

      # explicit no-duplicate-series guard for SC-037
      - alert: DuplicateDeviceSeries
        expr: count by (source, interface_name) (interface_traffic_rate_in_bps) > 1
        for: 5m
        labels: {severity: warning}
```

## 8. SRv6 items in FR-089/FR-094 — what survives, and the EVPN replacement

### 8.1 What SR Linux 25.10 actually has

SRv6 exists in the model set: `srl_nokia-srv6.yang` (system-level locators),
`srl_nokia-srv6-instance.yang` (`/network-instance[name=*]/segment-routing/srv6/instance[id=*]/
locator[locator-name=*]/{full-segment,micro-segment}/function/{end,end-x,end-dt4,end-dt6,end-dt2u,
end-dt2m,ua,udt4,…}`), `srl_nokia-srv6-isis.yang`, `srl_nokia-srv6-types.yang`
`[VERIFIED: srlinux-yang-models v25.10.3 file listing + generated paths/srv6.txt]`.

But: those modules contain **no per-SID, per-policy or per-MySID counter subtree**. Greps for
`statistics|counters` in the generated SRv6 path set return only unrelated interface/ethernet
counters `[VERIFIED: grep over paths/srv6.txt]`, and `srl_nokia-tunnel-tables.yang` contains no
`srv6` string `[VERIFIED: grep]`. The tunnel-table summary is typed
(`/network-instance[name=*]/tunnel-table/ipv{4,6}/tunnel-summary/tunnel-type[type=*]/…`) so it
*may* carry an SRv6 tunnel type `[UNVERIFIED: the identity set was not enumerated]`, but that is a
count of tunnels, not a MySID packet counter.

**Conclusion:** the SONiC-era FR-089/FR-094 items "SRv6 policy" and "MySID counters" have **no
direct SR Linux native equivalent** in 25.10 telemetry. Whatever the SRv6 decision is elsewhere in
this retarget, the *telemetry and visualization* requirements cannot be satisfied by renaming
paths. They must be deferred or replaced.

### 8.2 Recommended replacement: an **EVPN service-path view**

If SRv6 is deferred, strike "SRv6 policy and MySID" from FR-089's path list and "SRv6 service
state" from FR-094, and substitute a view that is fully backed by verified paths:

**Panel 1 — Service topology (VTEP-to-VTEP for one `mac-vrf`/`ip-vrf`).**
Variables: `$service` (a `network-instance` name), `$vni`.
- Anchor state: `network_instance_oper_state{network_instance_name="$service"}`
  and `network_instance_vxlan_interface_oper_state{network_instance_name="$service"}`
  `[paths: /network-instance[name=*]/oper-state, /network-instance[name=*]/vxlan-interface[name=*]/oper-state — VERIFIED]`
- EVPN instance health:
  `network_instance_protocols_bgp_evpn_bgp_instance_oper_state{network_instance_name="$service"}`
  with `…_evi` and `…_vxlan_interface` as info labels
  `[path: /network-instance[name=*]/protocols/bgp-evpn/bgp-instance[id=*]/{oper-state,evi,vxlan-interface} — VERIFIED]`
- Reachable VTEPs and their liveness:
  `rate(tunnel_vxlan_tunnel_vtep_statistics_in_packets[5m])` and `…_out_packets`, keyed by
  `source` × `vtep_address` — this is the literal VTEP-to-VTEP path matrix
  `[path: /tunnel/vxlan-tunnel/vtep[address=*]/statistics/* — VERIFIED]`

**Panel 2 — Per-VNI MAC distribution.**
`tunnel_interface_vxlan_interface_bridge_table_unicast_destinations_destination_statistics_active_entries`
keyed by `destination_vtep` × `destination_vni`
`[path: /tunnel-interface[name=*]/vxlan-interface[index=*]/bridge-table/unicast-destinations/
destination[vtep=*][vni=*]/statistics/{total,active,failed}-entries and .../mac-type[type=*]/... — VERIFIED]`
plus the local side
`network_instance_bridge_table_statistics_mac_type_active_entries{network_instance_name="$service"}`
split by `mac_type_type` (local learnt vs EVPN-learnt vs static)
`[path: /network-instance[name=*]/bridge-table/statistics/mac-type[type=*]/active-entries — VERIFIED]`.
These two together are the EVPN analogue of "which remote endpoint is this service reaching, and
how much of it".

**Panel 3 — Per-VNI / per-tunnel-interface state.**
`tunnel_interface_vxlan_interface_oper_state`, `…_oper_down_reason`, `…_ingress_vni`,
`…_egress_source_ip`
`[path: /tunnel-interface[name=*]/vxlan-interface[index=*]/{oper-state,oper-down-reason,ingress/vni,egress/source-ip} — VERIFIED]`.
Note again: **no counters at this level** — the counters are the VTEP ones from Panel 1. Any
requirement wording promising "per-VXLAN-interface statistics" must say "per-VTEP" instead.

**Panel 4 — ACL hit counters as the policy-path surface.**
`acl_acl_filter_entry_statistics_matched_packets` / `…_matched_octets`, keyed by
`acl_filter_name` × `acl_filter_type` × `entry_sequence_id`, and the interface-attached form
keyed additionally by `interface_interface_id` and direction
`[paths: /acl/acl-filter[name=*][type=*]/entry[sequence-id=*]/statistics/{matched-packets,
matched-octets,last-match} and /acl/interface[interface-id=*]/{input,output}/... — VERIFIED]`.
This is what the `acl` construct's "did my policy actually match" question needs, and it is the
nearest honest analogue to "MySID counters" (a per-policy-entry packet counter).

**Panel 5 — Drill-down from physical link → service.** The join is `source`: click a link cell in
the flow panel, carry `source` and `interface_name` into a data link that opens Panels 1–4
filtered by `source`, with `$service` derived from the subinterfaces present on that interface
(`interface_subinterface_oper_state{source=…, interface_name=…}`). FR-094's "drill-down from
physical links to EVPN … service state" is then implemented by a Grafana data link, not by a
second collection path.

### 8.3 Requirement wording deltas for §8

- **FR-089**: replace "interface, BGP, EVPN, IPv6, SRv6 policy and MySID, counter and system

- **FR-094**: replace "drill-down from physical links to EVPN and SRv6 service state" with

- **SC-036**: replace "physical-topology and SRv6 service-path views" with "physical-topology and
  EVPN service-path views", and keep the exact-match clause — §4.3 step 6 makes it testable.
