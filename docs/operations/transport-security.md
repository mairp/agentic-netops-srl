# Transport security: the SLIM gateway (FR-072, D-28, R-14)

The intent tier's agents talk to each other only through the SLIM gateway
(`deploy/agents/slim.yaml`, image `ghcr.io/agntcy/slim:0.6.1` pinned by digest in
`versions.lock.yaml`). The endpoint variable is `TRANSPORT_SERVER_ENDPOINT` =
`http://slim.agentic-netops-agents.svc:46357` (contracts/a2a-transport.md). Only the data-plane port
**46357/TCP** is exposed. The controller port 46358 is not a container port or a Service port, and
no NetworkPolicy admits it.

## What the design asked for, and what the pinned release does

D-28 asks for **mutual TLS**: server TLS plus client-certificate verification against a CA generated
in the cluster, with a gateway password from a generated Secret. The gate checked this before
anything was deployed (T166, `tests/gate/slim_tls_keys.sh`). The pinned release:

- **accepts server TLS** under the keys `cert_file` / `key_file`, and presents the configured
  certificate;
- **does not verify client certificates.** When `client_ca_file` was configured, a client **with no
  certificate** was still accepted (evidence
  `gate/qualifications/slim_tls_keys.json`: `client_without_certificate: accepted`,
  `client_certificate_verification_exposed: false`).

So the **R-14 fallback is in force**. This is an accepted risk with the production delta below. It is
not a silent downgrade.

## What runs (the R-14 fallback)

| Layer | What it gives | Where |
|---|---|---|
| **Server TLS** (TLS 1.3) with a certificate from an in-cluster CA | encryption in transit; clients check the gateway's identity (server name `slim.agentic-netops-agents.svc`) against the CA | cert-manager: Issuer `slim-selfsigned` → Certificate `slim-ca` → Issuer `slim-ca-issuer` → Certificate `slim-server` → Secret `slim-tls` (`ca.crt`, `tls.crt`, `tls.key`). The agents mount only `ca.crt`, read-only |
| **Gateway password** (HTTP Basic on the data-plane RPC) | refuses any client without the credential: no registration, no subscription, no delivery | Secret `slim-gateway` (`username`, `password`), generated by the tier's secret step with no literal. The gateway reads it through `${env:SLIM_GATEWAY_USERNAME}` / `${env:SLIM_GATEWAY_PASSWORD}` in `slim-config`, and those env vars come from `secretKeyRef`. Agents read it from the read-only mount `/var/run/secrets/agentic-netops/slim-gateway` |
| **NetworkPolicy `slim-ingress`** | only pods labelled `agentic-netops.io/tier: intent` can open a connection to 46357 | `deploy/rbac/networkpolicies.yaml` (US6), under `deny-all-by-default` |

`client_ca_file` is **deliberately not configured**. Setting an option the release ignores would
suggest that client certificates are verified when they are not.

**Proven live** on 2026-09-24. Records are under
`.evidence/agentic-netops_agentic-netops-fabric/20260924T084500Z-t082-t087/t082-slim-auth-*`:

- a tier pod with TLS and the right password registers, subscribes and gets messages delivered;
- a client with **no** password or a **wrong** password is refused. The gateway returns HTTP 401 on
  the data-plane RPC, the client logs
  `Status { code: Unauthenticated, message: "grpc-status header missing, mapped from HTTP status code 401" }`,
  and nothing it sends is delivered;
- a pod **without** the tier label cannot open a TCP connection to the gateway at all;
- a plaintext client, a client that trusts another CA, or a client dialling a name not in the
  certificate cannot connect;
- the Service has no port 46358.

**On the client side**, the pinned `slim_bindings` does not raise an error when the gateway refuses
it. `connect()` returns before the stream is authenticated. The tier therefore turns a refusal into
the transport authentication error (`common.exceptions.TransportAuthenticationError`) with an
explicit check after registration, and never infers success from `connect()` returning.

## What the fallback does not give (the residual risk)

1. **No per-agent identity at the transport.** Every agent holds the same gateway credential. A
   compromised agent can register under **any** card id, including another worker's topic, and
   receive or answer that worker's traffic. The gateway cannot tell mapper from deployer.
2. **A shared secret is not a workload identity.** Anyone who reads `slim-gateway` can join the
   transport from any tier-labelled pod. No tier identity can read Secrets through the API (no Role
   grants Secrets), so exposure means a node, the kubelet, or a mounted volume.
3. **NetworkPolicy is not an authenticator.** It limits *where* a connection may come from, by
   label. Anyone who can create a pod in `agentic-netops-agents` with the tier label passes it.
4. **The credential is fixed at the gateway's start.** `${env:…}` is resolved once, so rotating
   `slim-gateway` means restarting the gateway. Agents re-read their mounted copy and reconnect.

What the tier does **not** rely on the transport for: device actions. Neither tier identity can
express one (FR-075; `contracts/kubernetes-objects.md` §"Identity contract"). Every submission goes
through the Kubernetes API under RBAC and admission. A fully compromised transport can therefore
misroute or forge **agent messages**, but it cannot reach a device. The supervisor also
authenticates every operator request itself (FR-102).

## Production delta (what production must add)

A production deployment **must not** run this fallback as its transport security. It must do at
least one of the following:

- **Terminate the transport behind a service mesh with mutual TLS and workload identity** (for
  example SPIFFE/SPIRE-issued SVIDs, with an authorization policy that lets only the named
  ServiceAccount of each agent reach the gateway and only the supervisor call the workers). This is
  the delta D-28 names.
- **Or move to a SLIM release that verifies client certificates**, re-qualify it with
  `tests/gate/slim_tls_keys.sh` (the gate must then observe `client_without_certificate: refused`
  and `client_with_ca_signed_certificate: accepted`), issue **one certificate per agent** from the
  in-cluster CA with the agent's card id in the subject, configure `client_ca_file`, and retire the
  shared password.

In addition:

- bind each agent's certificate or identity to the **card id it may register**, so an agent cannot
  take another worker's topic;
- rotate the gateway credential (or certificates) on a schedule and restart the gateway on rotation;
- keep the NetworkPolicy. It stays useful as defence in depth, never as the authenticator.
