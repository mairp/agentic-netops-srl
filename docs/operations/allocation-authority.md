# The allocation authority

Every identifier the platform allocates — underlay loopbacks and point-to-point `/31`s, underlay
ASNs, service VLANs from the allocation band `1000–4000`, VNIs from `10000–20000` — is claimed from
exactly **one** allocation authority. Which one is data, not a flag: `versions.lock.yaml`
`allocationAuthority.kind` (data-model.md §23). Provisioning installs that one and no other, and
`make verify-compat` fails if both, or the wrong one, are present.

## Which authority runs: the first-party substitute

This tree runs **`allocationAuthority.kind: first-party`** — the first-party allocation authority,
the one permitted substitute for the pinned upstream kuid-server:

| | kuid (not installed) | first-party (installed) |
|---|---|---|
| Kinds | `IPIndex`/`ASIndex`/`VLANIndex`/`GENIDIndex` and their claims, `*.be.kuid.dev` (aggregated APIs) | `IdentifierPool` and `IdentifierClaim`, `fabric.agentic-netops.io/v1alpha1` (CRDs, `config/crd/conditional/`) |
| Namespace | `kuid-system` | `agentic-netops-allocation` |
| Workload | `kuid-server` | Deployment `allocation-authority` — the provider's own image (`srl-provider:<contentHash>`) with `SRL_PROVIDER_ROLE=allocation-authority` |
| Manifests | `deploy/kuid/`, seeds `deploy/kuid/indices/` | `deploy/allocation/`, seeds `deploy/allocation/pools/` |
| Provider's claim Role | `config/rbac/claims/kuid/` | `config/rbac/claims/first-party/` — `identifierclaims`: `get, list, watch, create, delete`; no `update`, no `patch` |

**Why.** Gate item G11 — the allocation claim round-trip — failed on the pinned kuid-server v0.0.13
on 2026-09-21: its scratch indices could not be created, so no claim could be bound, and
provisioning stopped naming G11 as FR-104 requires. The operator's decision to adopt the substitute
is recorded, with its reason and the failed-gate evidence, in
[docs/decisions/allocator-substitution.md](../decisions/allocator-substitution.md) and, in the
design, as **AD-74** (research.md). The lock file cites that record and the failed G11 evidence by
path and SHA-256 (`allocationAuthority.decisionRecord`, `allocationAuthority.failedGateEvidence`);
`make verify-pins` refuses `first-party` without both.

Every provisioning run warns the substitute by name, with its decision record and its failed-gate
evidence:

```text
[WARN ] ALLOCATION AUTHORITY SUBSTITUTED: versions.lock.yaml selects the first-party allocator substitute
        (IdentifierPool/IdentifierClaim in fabric.agentic-netops.io, namespace agentic-netops-allocation) instead of
        kuid-server — the one pin exception (FR-104, CD-03); decision record: docs/decisions/allocator-substitution.md,
        failed G11 evidence: docs/decisions/allocator-substitution/g11-observations.json
```

The substitute faces **G11 exactly as kuid did** — the same six observations and negative controls
(`tests/gate/g11_allocation_claim.sh`, against `identifierclaims` in `agentic-netops-allocation`).
If it fails, provisioning stops naming G11 with nothing above the authority installed: there is no
third authority. Its result is recorded per authority in the
[qualification record](../reference/qualification-record.md#g11-per-allocation-authority).

### How provisioning installs it (`AppsReady`)

1. the `srl-provider` image is built from the tree and loaded into the cluster; its content-hash tag
   is written into both `deploy/agentic-netops/kustomization.yaml` and
   `deploy/allocation/kustomization.yaml` (the authority and the provider run the same image);
2. `deploy/allocation` is applied (namespace, the two CRDs, the authority's RBAC, the Deployment);
   the CRDs are waited Established and the Deployment rolled out;
3. **G11** runs; on failure provisioning stops here;
4. the seed pools `deploy/allocation/pools` are applied — generated by
   `scripts/lib/inventory.sh --pools` from `deploy/kuid/indices`, so they carry exactly the kuid
   indices' names and ranges;
5. the device-configuration layer, then the provider with `config/rbac/claims/first-party`.

`deploy/kuid/` is never applied under `first-party`. The default `Fabric` (`examples/fabric/`) names
kuid pools; `FabricReady` applies it with each pool reference's group, kind and namespace rewritten
to `fabric.agentic-netops.io` / `IdentifierPool` / `agentic-netops-allocation` (names unchanged —
`gate::authority_pool_ref`), and the example file itself is not edited. `scripts/off.sh` removes the
namespace `agentic-netops-allocation` (ownership-checked) with the other owned resources.

## How to read a pool and a claim

```bash
kubectl -n agentic-netops-allocation get identifierpools,identifierclaims
make show-allocations          # the Fabric's allocations and the installed authority's pools and claims
```

A **pool** (`IdentifierPool`) is a numeric `spec.range` (`asn`, `vlan`, `vni`, `genid`) or an address
`spec.prefix` (`ip`). Its `status.allocations` is **the ledger** — the arbitration record: a value is
held exactly when an entry names it, with the holding claim's name and UID; `status.allocated` is the
count.

```bash
kubectl -n agentic-netops-allocation get identifierpool fabric01-vlan \
  -o jsonpath='{range .status.allocations[*]}{.value}{"\t"}{.claim}{"\t"}{.claimUID}{"\n"}{end}'
```

A **claim** (`IdentifierClaim`) names its pool (`spec.poolRef.name`) and, for a stated value,
`spec.requested` (a number, or an address/prefix for `ip`; `spec.prefixLength` for a dynamic `ip`
claim). Its `spec` is immutable — a claim is never moved, only deleted and re-created. The allocated
value is `status.value`; the `Ready` condition says why:

| `Ready` | Reason | Meaning |
|---|---|---|
| `True` | `Bound` | `status.value` is held by this claim in the pool's ledger |
| `False` | `Conflict` | the stated value is held by another claim; the message names it as `value <v> is held by claim <namespace>/<holder>`. The claim binds on its own once the holder is deleted |
| `False` | `OutOfRange` | the stated value is outside the pool |
| `False` | `Exhausted` | a dynamic claim against a pool with no free value |
| `False` | `Invalid` | the claim, or its pool, cannot be evaluated as written |
| `Unknown` | `PoolNotFound` | the named pool does not exist; re-evaluated when it does |

A dynamic claim gets the lowest free value, never below the pool's start. Deleting a claim frees its
value synchronously: the finalizer `fabric.agentic-netops.io/identifier-release` removes the ledger
entry, and `kubectl delete` returns only once it has. A claim that reports no value is terminal to
every consumer — nothing proceeds on an unknown identifier. Labels a consumer selects on live in
`metadata.labels` (there is no `spec.labels`).

```bash
kubectl -n agentic-netops-allocation get identifierclaims \
  -o custom-columns='CLAIM:.metadata.name,POOL:.spec.poolRef.name,VALUE:.status.value,READY:.status.conditions[?(@.type=="Ready")].status,REASON:.status.conditions[?(@.type=="Ready")].reason'
```

## Returning to kuid

A return to the upstream authority is the same decision in reverse, and is recorded the same way:

1. append a dated **`## <YYYY-MM-DD> return`** entry to
   [docs/decisions/allocator-substitution.md](../decisions/allocator-substitution.md), with a
   `Reason:` line (the latest-dated entry is the record's state);
2. set `allocationAuthority.kind: kuid` in `versions.lock.yaml` (and drop `decisionRecord` /
   `failedGateEvidence`, which are admitted only with `first-party`).

`make verify-pins` enforces it: `kind: kuid` while the record's latest entry is an adoption is
refused, as is `first-party` without both references.

**It needs a lab that holds no bound claim.** No claim survives a change of authority and none is
migrated. When the lock selects an authority other than the one installed, provisioning lists the
bound claims the installed one holds and, if there is any, stops non-zero before touching either
authority, naming each service that rests on one — remove those services first, re-provision, then
re-create them. With none bound it removes the installed authority and installs the other. The
returned kuid then faces G11 like any authority: a return is not evidence that it passes.
